# Pin the models, pre-render, prove one scene

The best pipeline on 25 November 2026 is a four-stage, script-driven chain: ElevenLabs **Eleven v4** rendered scene by scene through the Text to Dialogue with-timestamps endpoint, stills generated through the **OpenAI Images API edits endpoint** (GPT-Image-2.6 Sunburst at 1440x2560 with reference sheets on every call), picture composed in **Remotion 4.0.547** with audio mastered in ffmpeg, and delivery as **two pre-rendered H.264 MP4s per episode** (Hindi and English) played by a plain `<video>` element in Next.js 16 with a React subtitle overlay fed by caption JSON. Three findings overturn likely starting assumptions: Eleven v4 replaced v3 as flagship on 28 September 2026, so the "v3 vs Multilingual v2" choice is stale; the Codex CLI's built-in image tool works without an API key but exposes no size, quality, model or seed control and returns roughly 1.5-megapixel images, so it suits reference sheets but not 250–400 production frames; and ffmpeg's `zoompan` filter jitters on slow zooms, which rules it out for the camera moves while leaving it the right tool for ducking and loudness. Every relevant ElevenLabs API default points at an older or deprecated model, and the image script bundled with Codex still defaults to `gpt-image-2`, so each request must set `model_id` or `model` explicitly. The whole job is cheap — on the order of $99 for a month of ElevenLabs Pro and an estimated $40–155 of image generation — so the real risks are quality and rights, not budget. None of the sources tested v4 on Hindi, on Devanagari lines with Latin-script English words, or with audio tags inside Hindi text; none measured character consistency across dozens of reference-conditioned frames; and the Eleven Music terms exclude "film, TV" on every self-serve plan. A single proof scene of about ten shots, rendered in both styles and both languages, must settle those questions before full production.

## Eleven v4 dialogue, rendered scene by scene, carries the performance

### One request per scene gives interplay, cut points and timing together

ElevenLabs' models page now lists **`eleven_v4` as the flagship**, with 90+ languages including Hindi (`hi`), audio tags, multi-speaker dialogue and a 100,000-character request limit, while `eleven_v3` is labelled "previous generation" (5,000 characters) and `eleven_turbo_v2_5` and `eleven_turbo_v2` are deprecated ([ElevenLabs Models](https://elevenlabs.io/docs/overview/models)). v4 launched on 28 September 2026 and is live in the API ([ElevenLabs blog: Introducing Eleven v4](https://elevenlabs.io/blog/eleven-v4)); press coverage named Japanese, Brazilian Portuguese, Mandarin and Cantonese as the biggest quality gainers, not Hindi ([TechCrunch](https://techcrunch.com/2026/09/28/elevenlabs-new-v4-speech-model-supports-more-expression-control-and-90-languages/)). The recommendation of v4 for Hindi therefore rests on ElevenLabs' positioning, with `eleven_v3` as the A/B arm and `eleven_multilingual_v2` (29 languages, no tags, "most stable on long-form generations") as the safe fallback.

The right unit of generation is the scene. `POST /v1/text-to-dialogue/with-timestamps` takes an ordered `inputs` array of `{text, voice_id}` turns and returns one continuous performance plus character-level `alignment` and per-turn `voice_segments` with start and end times, which double as edit points and subtitle cue boundaries ([Text to Dialogue with-timestamps API reference](https://elevenlabs.io/docs/api-reference/text-to-dialogue/convert-with-timestamps)). The binding limit is **2,000 total characters per request** for reliable generation, and the API reference caps a request at 10 unique voice IDs, although the capability page claims no speaker limit ([Text to Dialogue API reference](https://elevenlabs.io/docs/api-reference/text-to-dialogue/convert); [Text to Dialogue capability page](https://elevenlabs.io/docs/overview/capabilities/text-to-dialogue)). A two-minute episode runs to roughly 1,500–2,200 characters before tags, so it splits into two to four scene requests chained with `previous_request_ids` (up to three) for continuity ([Text to Dialogue with-timestamps API reference](https://elevenlabs.io/docs/api-reference/text-to-dialogue/convert-with-timestamps)). Output is nondeterministic even with a `seed` ([Text to Dialogue capability page](https://elevenlabs.io/docs/overview/capabilities/text-to-dialogue)), so the script should store audio, alignment, request ID and seed for every take and budget two to four takes per emotional scene.

### Emotion comes from English bracket tags, punctuation and multiple takes

Audio tags are free-form English directions in square brackets placed before or after the text they affect, such as `[whispers]`, `[angry]`, `[sighs]` or stacked forms like `[excited, happy]`; they work only on v4, v4 Turbo, v3 and v3 Conversational, are not an enum, and are "not always followed" ([ElevenLabs prompting guide](https://elevenlabs.io/docs/best-practices/prompting/eleven-v3); [ElevenLabs blog: Introducing Eleven v4](https://elevenlabs.io/blog/eleven-v4)). v4 and v3 do not support SSML break tags, so pauses come from ellipses, `[pause]`-style tags and sentence structure, and CAPITALS add emphasis ([ElevenLabs TTS best practices](https://elevenlabs.io/docs/overview/capabilities/text-to-speech/best-practices)). ElevenLabs publishes no Hindi-specific tag guidance, so the working convention is English tags inside Devanagari lines, validated per voice. Inline sound-effect tags such as `[phone buzzing]` exist, but they bake effects into the dialogue stem and corrupt both mixing and alignment; effects belong on their own track.

Code-mixed input has no official guidance at all. The available levers are `language_code: "hi"` (supported on v3, v4 and Flash, not on Multilingual v2), alias-type pronunciation dictionaries, and text normalisation control ([TTS with-timestamps API reference](https://elevenlabs.io/docs/api-reference/text-to-speech/convert-with-timestamps); [ElevenLabs TTS best practices](https://elevenlabs.io/docs/overview/capabilities/text-to-speech/best-practices)). The one practitioner source found, written a week before v4, reports that a Devanagari sentence with an occasional Latin-script English word "generally reads acceptably" on v3, while Hinglish typed entirely in Latin letters sounds poor ([BundledSEO ElevenLabs review](https://bundledseo.com/blog/elevenlabs-review/)). That matches the project's script convention, which should stay. Where the Hindi voice mangles an English word, an alias that maps the Latin spelling to a Devanagari respelling fixes the audio while the subtitle keeps the Latin form. Numbers, dates and currency should be spelled out in the script rather than left to normalisation.

### Subtitles come from character alignment grouped into words

No ElevenLabs TTS or dialogue response contains word-level timing. Both with-timestamps endpoints return parallel arrays of characters with start and end times, for the original text and for the normalised text ([TTS with-timestamps API reference](https://elevenlabs.io/docs/api-reference/text-to-speech/convert-with-timestamps)). The subtitle builder should walk the original-text `alignment`, split on whitespace only, and take the first character's start and the last character's end per word; this keeps Devanagari matras and conjuncts inside one token and reproduces Latin-script English words exactly as scripted. Forced Alignment is the cross-check: it returns ready-made `words` with a `loss` score, lists Hindi among its supported languages, and is billed at the speech-to-text rate of $0.20 per audio hour, which is negligible here ([Forced Alignment capability page](https://elevenlabs.io/docs/overview/capabilities/forced-alignment); [ElevenLabs API pricing](https://elevenlabs.io/pricing/api)). Its documentation says nothing about mixed-script text, and whether the generation-time alignment arrays include bracketed tag characters is undocumented. Both are proof-scene tests.

### Casting, score and effects are solved; the music licence is not

The Voice Library endpoint returns, for each voice, `verified_languages` entries with language, `model_id` and accent, which is the data-driven way to find a voice verified for both Hindi and English, plus a creator-set `notice_period` and any custom `rate` ([List shared voices API reference](https://elevenlabs.io/docs/api-reference/voices/voice-library/get-shared)). Voice owners can withdraw a shared voice subject to that notice period ([Voice Library Addendum](https://elevenlabs.io/vla)), so lead characters are safer on voices with long notice periods or on voices the production controls. No authoritative list of strong Hindi voices exists; shortlisting is by audition.

Eleven Music and Sound Effects cover the functional need. Music costs $0.15 per minute and effects $0.12 per minute at API list price, effects cap at 30 seconds per generation with a `loop` flag for longer beds, and `music_v1` and `eleven_text_to_sound_v2` are both scheduled for removal in early 2027 ([ElevenLabs API pricing](https://elevenlabs.io/pricing/api); [Sound effects capability page](https://elevenlabs.io/docs/overview/capabilities/sound-effects); [Eleven Music capability page](https://elevenlabs.io/docs/overview/capabilities/music)). A small reusable cue library — a theme, a handful of mood beds and stingers — serves a series better than scoring each episode afresh. The constraint is legal: the Music Terms, updated 9 October 2026, grant Free through Business plans "All online and offline commercial use permitted, except film, TV, radio, and Studio Games", and describe Starter, Creator and Pro as "individual use only" ([Eleven Music Terms](https://elevenlabs.io/music-terms)). Whether an app-distributed micro-drama counts as "film" or "TV" was not established, and Sound Effects terms were not found. A company producing a commercial series needs that answered in writing, an Enterprise Music licence, or music from elsewhere.

**Pro at $99 per month** is the sensible tier: 600,000 credits, 10 concurrent requests and 44.1 kHz PCM/WAV output through the API, which lower plans lack ([ElevenLabs pricing](https://elevenlabs.io/pricing)). At one credit per character and ElevenLabs' own equivalence of about 1,000 characters per minute, 70 minutes of final speech is roughly 70,000 credits, or 210,000–280,000 with three to four takes; that doubles if 70 minutes means per language. These figures are estimates, since Devanagari characters-per-minute was not measured. The batch runner should use the official Python or Node SDK at v2.70.0 or later; the official CLI and the hosted MCP server at `https://api.elevenlabs.io/v1/mcp` suit casting and exploration, not unattended rendering ([ElevenLabs libraries page](https://elevenlabs.io/docs/eleven-api/resources/libraries.md); [ElevenLabs changelog 2026-09-28](https://elevenlabs.io/docs/changelog/2026/9/28.md); [ElevenLabs changelog 2026-08-22](https://elevenlabs.io/docs/changelog/2026/8/22.md)).

## The Images API renders the frames; Codex builds only the reference sheets

### Codex generates images today but gives away every control that matters

Codex CLI 0.160.1 on the project Mac has a built-in image tool that works with the existing ChatGPT login and no API key, and 146 images already sit under `~/.codex/generated_images/` ([local inspection: imagegen SKILL.md](file://~/.codex/skills/.system/imagegen/SKILL.md)). Its actual tool signature accepts only a prompt, reference image paths and a transparent-background flag: no size, aspect ratio, quality, model or seed ([local inspection: session log](file://~/.codex/sessions/2026/11/25/rollout-2026-11-25T20-29-43-01a21338-4073-7cf1-8d0a-a2fefc1de9a0.jsonl)). The saved vertical images measure about 1.5–1.6 megapixels — `941x1672`, `910x1728`, `853x1844` — which is below 1080x1920 and only sometimes exactly 9:16, and six consecutive generations took between 34 and 139 seconds each ([local inspection: generated images](file://~/.codex/generated_images)). Image turns consume the shared plan allowance "3-5x faster on average" than ordinary turns, with no published per-plan image count ([OpenAI Codex pricing docs](https://learn.chatgpt.com/docs/pricing)).

Headless use is the weak point. Those local images came from the Codex desktop app, not from `codex exec`. Third-party sources conflict on whether headless runs write the PNG to disk at all, and a reported issue describes a non-interactive run that asked for six images, produced two, placed none at the requested paths and still exited with code 0 ([skills.sh codex-image-gen](https://www.skills.sh/shipshitdev/skills/codex-image-gen); [Aident write-up of openai/codex #37717](https://aident.ai/blog/fix-codex-exec-exits-zero-missing-image-artifact)). The Codex route therefore fits the few, heavily scrutinised assets — character turnarounds, location plates, style plates — and the API route fits the 250–400 shot frames.

### GPT-Image-2.6 Sunburst at 1440x2560 removes the need for upscaling

OpenAI's current API image models are `gpt-image-2.6-sunburst` and `gpt-image-2.6-flare` (4 November 2026), alongside the 2.5 pair and `gpt-image-2`, all at **$30 per million image-output tokens** ([OpenAI API pricing](https://developers.openai.com/api/docs/pricing); [OpenAI, Introducing Images 2.6](https://openai.com/index/introducing-images-2-6/)). OpenAI positions Sunburst for "higher-quality generation and greater consistency across edits" and Flare for speed, and warns that the two families' outputs differ, so one model must serve a whole series ([OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)). Sizes are custom `WIDTHxHEIGHT` strings whose edges are multiples of 16, up to 3840 pixels per edge ([OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)). That makes `1080x1920` invalid and **`1440x2560` the practical choice**: exact 9:16, a 1.33x margin over the delivery frame for slow push-ins and pans, and the largest 9:16 size not flagged experimental on GPT-Image-2.5. Slow micro-drama moves of 5–15% fit comfortably inside that margin. The Codex built-in route would instead need a 2x upscale, which adds resolution but no true detail.

Cost is minor. OpenAI publishes per-image prices only for `gpt-image-2` — $0.041 at medium and $0.165 at high for `1024x1536` — and states that 2.5 token rates match ([OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation); [OpenAI model page: GPT-Image-2.5 Sunburst](https://developers.openai.com/api/docs/models/gpt-image-2.5-sunburst)). Scaling by pixel count gives an estimated $0.10–0.39 per `1440x2560` frame, or **roughly $40–155 for 400 frames** before reference-image input tokens and retakes; recording the `usage` field on real calls replaces this estimate. If a dated snapshot matters more than the newest model, `gpt-image-2.5-sunburst-2026-09-08` is the pinnable alternative and documents Batch support at half price, which the 2.6 model page does not.

### Consistency is a reference-image discipline, not a model feature

There is no seed parameter and no trained-character feature, and OpenAI states that the model "may occasionally struggle to maintain visual consistency for recurring characters" ([OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)). The documented method is to create a reusable character reference, pass it as an input on every new scene, identify each input image "by number and purpose", restate defining details and add "Do not redesign the character" ([OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)). The edits endpoint, `POST /v1/images/edits`, accepts up to 16 images ([OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)), which comfortably holds the asset hierarchy this project needs: one approved turnaround sheet and face close-up per character and costume, one or two empty master plates per location, and one style plate per series.

Independent evidence sharpens the practice. A single-run vendor test of GPT Image 2.5 found that props and set dressing drift more than faces — a ceramic cup became a paper cup, a counter changed colour — that errors in the reference sheet replicate into every frame, and that camera-position phrases such as "high angle" were not reliably followed; describing what is visible in frame worked better ([JXP storyboard test](https://www.jxp.com/gpt-image/blog/gpt-image-2-5-storyboard)). A 26-model benchmark found character consistency the lowest-scoring capability across the field, with GPT Image 2.5 Sunburst in the leading group at 4.72 of 5 behind Seedream 5.0 Pro at 4.86 ([IMG.LY consistency findings](https://img.ly/ai-benchmarks/findings/consistency.md)); that test used text descriptions without reference images, so it does not justify switching provider. Three rules follow. Every shot anchors to the original approved references rather than to the previous frame, because OpenAI warns that "Repeated edits can drift". Every prompt names every prop that must persist. Fixes are targeted edits with stated invariants and `complexity: "low"`, which OpenAI says keeps surrounding details intact.

The two styles need different fixed blocks. For photoreal frames OpenAI advises asking explicitly for a "real photograph", using lens and lighting words as appearance cues, describing visible skin texture and worn materials, and excluding glamorisation and heavy retouching ([OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)). For flat illustration it advises naming medium, line quality and proportions in a labelled "Style:" section, asking for flat design with strong silhouettes, and avoiding gradients. A cel-shaded series should therefore carry a verbatim style block covering outline weight, two-tone hard-edged shading and a named palette, an explicit exclusion of 3D and painterly rendering, and the style plate attached to every call as a style-only reference. No source tested South Asian faces, Indian settings, Devanagari signage or cel-style stability over dozens of frames, so signage should be kept illegible and the proof scene must supply the missing evidence.

### A manifest-driven runner makes 400 frames resumable and auditable

A moderation block is a hard error — `error.code = "moderation_blocked"` with optional stage and category details — that OpenAI says must not be retried without changing the prompt, while rate-limit and server failures retry with backoff ([OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)). The usage policies protect anyone under 18 from sexual or violent contexts and restrict photoreal likeness of real people ([OpenAI Usage Policies](https://openai.com/policies/usage-policies/)), and developers report false positives on innocuous prompts even with `moderation: "low"` ([OpenAI community thread](https://community.openai.com/t/api-issue-moderation-over-refusals-on-gpt-image-2-with-moderation-low-where-chatgpt-always-succeeds/1388964)). A drama should state adult ages in every prompt, keep minors out of violent or romantic frames, show aftermath rather than injury, use generic uniforms, and set `moderation: "low"`.

The runner should be a custom script around a `shots.jsonl` manifest: one row per frame with shot ID, rendered prompt, reference asset IDs, size, quality, status, attempts, output path, hash, token usage and error code. It skips rows whose output already validates, never overwrites a take, routes blocked shots to a rewrite queue, and runs three to five requests in parallel, well inside the 20-images-per-minute Build-tier limit documented for 2.5 Sunburst ([OpenAI model page: GPT-Image-2.5 Sunburst](https://developers.openai.com/api/docs/models/gpt-image-2.5-sunburst)). The batch script bundled with Codex is not a substitute: its `generate-batch` mode has no reference-image support and defaults to `gpt-image-2` ([local inspection: imagegen cli.md](file://~/.codex/skills/.system/imagegen/references/cli.md)). The API route requires one thing the team lacks today: an `OPENAI_API_KEY` on a billed organisation, with organisation verification where prompted.

## Remotion moves the camera while ffmpeg masters the sound

### React transforms give smooth moves that zoompan cannot

Remotion is the best-supported tool for this exact job. Every frame is a deterministic function of the frame number, camera moves are browser-composited transforms with any easing curve, captions are a first-party package styled in HTML and CSS, and the same composition serves both MP4 render and in-browser preview ([Remotion: Captions](https://www.remotion.dev/docs/captions/)). The current release is `remotion@4.0.547` (24 November 2026), every `@remotion/*` package must be pinned to the identical version, and version 5.0 is documented as not yet released with changed defaults ([npm: remotion](https://www.npmjs.com/package/remotion); [Remotion: Upgrading](https://www.remotion.dev/docs/upgrading); [Remotion: v5.0 migration](https://www.remotion.dev/docs/5-0-migration)). It is free for individuals and teams of up to three people; a larger for-profit team pays $25 per seat per month for manual rendering, and for such a team embedding the Remotion Player in a product falls under a separate plan with a $100 monthly minimum ([Remotion: Licence and pricing](https://www.remotion.dev/docs/license/pricing)). Contractors on the project count toward headcount ([Remotion licence FAQ](https://www.remotion.dev/docs/license/faq)).

Plain ffmpeg fails on the picture side. Its `zoompan` filter produces shaky output on slow zooms, a sub-pixel rounding defect tracked in a ticket open for about ten years, and the standard workaround is to upscale the input several times before zooming at high memory cost ([FFmpeg trac #4298](https://trac.ffmpeg.org/ticket/4298)). Burning in Hindi text through ffmpeg additionally requires libass built with HarfBuzz, without which Indic conjuncts break ([FFmpeg trac #8738](https://lists.ffmpeg.org/pipermail/ffmpeg-trac/2020-June/054649.html)); a local check found that the Homebrew ffmpeg 8.1.1 on the project Mac has no libass, FreeType or HarfBuzz at all. The alternatives are weaker fits: Motion Canvas's core package last shipped in February 2025, Editly's last release dates from January 2025, and Revideo's repository has moved under a commercial editor ([npm: @motion-canvas/core](https://www.npmjs.com/package/@motion-canvas/core); [npm: editly](https://www.npmjs.com/package/editly); [GitHub: midrender/revideo](https://github.com/midrender/revideo)). Real-time composition in the browser is attractive for instant language switching but is the most fragile path on iPhones, where Remotion's own documentation calls Mobile Safari the strictest browser and warns that audio starting later in the timeline can be blocked ([Remotion: Player autoplay](https://www.remotion.dev/docs/player/autoplay)).

The composition should be data-driven from the audio. ElevenLabs `voice_segments` supply line timings, which set shot durations and caption cues, so each language renders from the same components with its own timing file. Because Hindi and English lines differ in length, rendering the picture once per language is cleaner than forcing one language onto the other's cut; this is a design recommendation rather than a sourced finding. One conversion step is custom: Remotion's `elevenLabsTranscriptToCaptions()` accepts ElevenLabs speech-to-text output and does not document support for the TTS with-timestamps response, so the pipeline needs a small function that turns character alignment into `Caption` objects ([Remotion: elevenLabsTranscriptToCaptions](https://www.remotion.dev/docs/elevenlabs/elevenlabs-transcript-to-captions)). For a handful of episodes, local rendering beats AWS Lambda on simplicity, although Remotion's published examples show a one-minute video rendering on Lambda for $0.017 in under 19 seconds ([Remotion: Lambda cost examples](https://www.remotion.dev/docs/lambda/cost-example)).

One planning check deserves attention. Vendor pacing guidance for vertical drama gives an average shot of about 3–5 seconds, far faster than long-form television ([Axis AI Studios](https://www.axisaistudios.com/blog/editing-vertical-dramas-pacing-and-cut-rhythm)), which implies roughly 25–35 stills for a two-minute episode once slow moves hold slightly longer. A budget of 250–400 frames therefore covers about 7–16 episodes at that density. If the season is longer, either the frame budget rises or stills hold for 10 seconds or more, and that pacing should be judged in the proof scene.

### Parallax and image-to-video are hero-shot upgrades, not the baseline

Depth-based parallax is scriptable: estimate a depth map with Depth Anything V2 or Apple's Depth Pro, then either render with DepthFlow, an open-source image-to-parallax tool, or split the still into inpainted layers and animate them at different rates in Remotion ([GitHub: Depth-Anything-V2](https://github.com/DepthAnything/Depth-Anything-V2); [GitHub: DepthFlow](https://github.com/BrokenSource/DepthFlow)). DepthFlow is AGPL-3.0, and the largest Depth Anything 3 checkpoints are non-commercial ([HF: da3-giant](https://huggingface.co/depth-anything/da3-giant)), so licences need a check before adoption. Engineering judgement, not benchmark data, says displacement parallax holds only for small, slow camera travel and suits photoreal stills better than flat illustration, where explicit character and background layers are the safer route.

Image-to-video has moved on from the models most guides name. One aggregator's November 2026 survey lists Kling 4.0, Seedance 2.5, Wan 3.0, Veo 3.1 and Runway Gen-4.5 at roughly $0.05–0.25 per second at 720p, and secondary reports say the Sora 2 API was removed on 24 September 2026 ([Teamday: best AI video models](https://www.teamday.ai/blog/best-ai-video-models-2026); [DEV: Sora 2 shutdown](https://dev.to/mr_manushukla/sora-2-and-the-videos-api-shut-down-on-24-september-2026-the-migration-and-the-real-cost-per-second-bek)). Those prices were not checked on vendor pages. Animating an entire two-minute episode works out to an estimated $15–60 per take, against near zero for camera moves on stills, and a comparison of the field itself concludes that specifications do not reveal motion quality and finalists must be tested on one's own images ([OpenRouter: image-to-video models compared](https://openrouter.ai/blog/insights/image-to-video-models-compared/)). The sensible use is three to six animated clips per episode — the opening hook, an emotional close-up, the cliffhanger — with the models' own audio switched off.

### One ffmpeg chain masters both languages to the same loudness

No mobile short-video platform publishes a loudness specification; **-14 LUFS integrated with a -1 dBTP ceiling** is the most widely cited target ([Fora Soft: LUFS targets per platform 2026](https://www.forasoft.com/learn/audio-for-video/articles-audio/lufs-targets-per-platform-2026)). The scripted chain per language builds three stems (dialogue, music, effects), ducks music under dialogue with `sidechaincompress` keyed by that language's own dialogue stem, mixes with `amix`, then runs two-pass `loudnorm` with `I=-14:TP=-1:LRA=11`, feeding the first pass's measured values into the second and setting the output sample rate explicitly because dynamic mode upsamples to 192 kHz ([FFmpeg filters: sidechaincompress](https://ffmpeg.org/ffmpeg-filters.html#sidechaincompress); [FFmpeg filters: loudnorm](https://ffmpeg.org/ffmpeg-filters.html#loudnorm)). Starting values of `threshold=0.03:ratio=8:attack=20:release=400` for the ducker are tuning points, not sourced standards. Running the identical chain for Hindi and English guarantees no level jump when the viewer switches language. Forced Alignment, where used, runs on the clean dialogue stem, never on the mix.

## Two MP4s per episode and a DOM overlay make language switching trivial

For a polished demo, each episode ships as a pre-rendered 1080x1920 H.264 MP4 per language, played by a plain `<video playsInline>`. Mux's own guidance says MP4 is more compatible and easier to preload for short clips, with HLS reserved for longer content or adaptive quality ([Mux: background video guidelines](https://www.mux.com/articles/guidelines-for-better-website-background-videos)). Switching language then means swapping `src`, seeking to the saved `currentTime` and resuming inside the same tap handler. HLS with alternate audio renditions is the textbook streaming answer, but an open Apple Developer Forums report describes iOS 26 native HLS falling back to the default track when alternates are selected, with no Apple reply ([Apple Developer Forums thread 818465](https://developer.apple.com/forums/thread/818465)). Two files cost double storage and a brief rebuffer; they do not depend on an unresolved platform bug. Current package versions are `next@16.4.6` and `react@19.3.1` ([npm: next](https://www.npmjs.com/package/next)).

Sound rules dictate the interaction design. iOS plays video without a gesture only when it is muted or has no audio track, and un-muting without a gesture pauses playback ([WebKit: New video policies for iOS](https://webkit.org/blog/6784/new-video-policies-for-ios/)); Chrome allows sound once the user has interacted with the domain and expects code to handle a rejected `play()` promise ([Chrome autoplay policy](https://developer.chrome.com/blog/autoplay)). The player should therefore open on a poster with an explicit tap to play, call `play()` inside the gesture handler on every swipe to the next episode, and fall back to muted playback with a "tap for sound" control when the promise rejects. Next.js guidance adds `preload="none"` with a `poster` and a fixed `aspect-ratio` to prevent layout shift ([Next.js: videos guide](https://nextjs.org/docs/app/guides/videos)), and only the next episode should be kept warm, mirroring the adjacent-preload strategy Meta describes for Reels ([Android Developers Blog](https://android-developers.googleblog.com/2026/03/instagram-and-facebook-deliver-instant.html)).

Subtitles belong in a React overlay, not in the video and not in native WebVTT. Burned-in text cannot switch language. Native `::cue` styling is inconsistent across browsers, karaoke-style captions are unsupported out of the box, and Chrome and Safari ignore WebVTT line and position alignment ([npm: media-captions README](https://www.npmjs.com/package/media-captions); [W3C WebVTT implementation report](https://www.w3.org/wiki/TimedText/WebVTT_Implementation_Report)). The overlay reads the same caption JSON the Remotion composition uses, one file per language, and syncs to the video clock. Browser text shaping then handles Devanagari conjuncts and mixed Hindi–Latin runs, provided a font covering both scripts is loaded and `lang="hi"` is set. Word highlighting must tokenise on whitespace and never per character, and letter-spacing or per-letter transforms should be avoided on Devanagari. Subtitle language and audio language become independent toggles at no extra cost.

Hosting scales with ambition. Vercel Blob on the Hobby plan includes 10 GB of transfer per month and blocks access for 30 days when exceeded rather than billing, which suits only a privately shown demo ([Vercel Blob pricing](https://vercel.com/docs/vercel-blob/usage-and-pricing)). Mux's free plan stores up to 10 on-demand assets with 100,000 delivery minutes a month and supports alternate audio tracks on one asset through its player ([Mux pricing](https://www.mux.com/pricing); [Mux: alternate audio tracks](https://www.mux.com/docs/guides/add-alternate-audio-tracks-to-your-videos)), but that route inherits the HLS audio-switching question on iOS and needs a device test first.

## Thirteen unknowns the proof scene must settle

A caveat applies to everything above. The research read vendor pages on 24–25 November 2026 through an automated page reader that summarises and quotes, so any string destined for code — model IDs, parameter names, limits — needs re-checking against the live page. Several load-bearing products are under two months old (Eleven v4, GPT-Image-2.6), official documents contradict each other in places (dialogue speaker limits, music maximum duration, ElevenLabs plan allowances between its two pricing pages), and no image, audio or video was generated during the research. The proof scene should be one scene of about ten shots with two characters in one location, rendered in both visual styles and both languages, including about twenty deliberately code-mixed Hindi lines.

## Conclusion

The pipeline's hard problems are not where the tooling looks hardest. Assembly and delivery are settled engineering: Remotion, a two-pass loudness chain, MP4 files and a DOM overlay involve no open research questions, only device testing. The uncertainty concentrates in two places that no vendor document resolves — whether a model released eight weeks ago performs Hindi drama with English words convincingly, and whether reference-conditioned image generation holds a cast, their props and a drawing style steady across hundreds of frames. Both are perceptual judgements that only a rendered scene and a human audience can make, which is why the proof scene is the first production task rather than a formality before it.

The architecture also yields a property worth protecting: the audio alignment data is the single timeline from which shot durations, caption cues and ducking all derive. Keeping that data as the source of truth, with model IDs, seeds, prompts and reference hashes logged per take, means a new model release — likely, given that both vendors shipped flagship updates within the past ten weeks — triggers a re-render of affected assets rather than a rebuild of the pipeline. The one item that code cannot fix is the music licence, and it should go to ElevenLabs in writing before any cue is composed.
