# Image generation for ~250–400 consistent 9:16 story frames via OpenAI Codex CLI / OpenAI image models (state as of 25 Nov 2026)

Reading notes for the report writer:
- "Local inspection" sources are read-only checks made on the team's own Mac on 25 Nov 2026 (Codex CLI `0.160.1`, logged in with ChatGPT, no `OPENAI_API_KEY`). They are primary evidence for this machine but are not published documentation.
- OpenAI's developer docs now partly redirect from `developers.openai.com/codex/...` to `learn.chatgpt.com/docs/...`.
- Model naming moved fast in 2026: `gpt-image-2` (21 Apr 2026) -> GPT-Image-2.5 Flare/Sunburst (8 Sep 2026) -> GPT-Image-2.6 Flare/Sunburst (4 Nov 2026). Many third-party guides still describe `gpt-image-2`; treat anything dated before September 2026 as possibly stale.
- No image was generated during this research (to avoid spending the team's quota). Everything about headless `codex exec` behaviour is therefore from documents and third-party reports, not from a live test.

## 1. Can Codex CLI (~0.160) generate images directly? Mechanism, flags, output location, model, ChatGPT-login, limits

### Takeaway
Yes. Codex has a built-in image tool (`image_gen` / `image_gen.imagegen`, invoked through the bundled `$imagegen` skill) that works with a ChatGPT login and needs no API key; on this Mac the feature flag `image_generation` is `stable / true` and 146 images already sit under `~/.codex/generated_images/`. The built-in tool exposes almost no controls (prompt, reference image paths, transparent background only — no size, quality, model or seed), images count against the plan's shared Codex usage at "3-5x" the rate of a normal turn, and there are conflicting reports on whether headless `codex exec` reliably writes the PNG to disk, so a one-image smoke test is required before building a batch on it.

### Cited Findings

**Mechanism and modes**
- The bundled skill defines exactly two modes: "Default built-in tool mode (preferred): built-in `image_gen` tool ... Does not require `OPENAI_API_KEY`" and "Fallback CLI mode: `scripts/image_gen.py` CLI ... Requires `OPENAI_API_KEY`", with fallback subcommands `generate`, `edit`, `generate-batch`. — [local: imagegen SKILL.md](file://~/.codex/skills/.system/imagegen/SKILL.md)
- The skill tells the agent: "The word `batch` by itself does not mean CLI fallback ... stay on the built-in path and issue one built-in call per requested asset or variant", and "If the built-in tool fails or is unavailable, tell the user the CLI fallback exists and that it requires `OPENAI_API_KEY`. Proceed only if the user explicitly asks for that fallback." — [local: imagegen SKILL.md](file://~/.codex/skills/.system/imagegen/SKILL.md)
- Installed version is `codex-cli 0.160.1`; `codex login status` prints "Logged in using ChatGPT"; `OPENAI_API_KEY` is unset; `codex features list` shows `image_generation   stable   true`. — [local: `codex --version`, `codex login status`, `codex features list`](file://~/.local/bin/codex)
- The built-in tool's actual declaration (captured from a session log on this Mac) is `image_gen__imagegen(args: { prompt: string; referenced_image_paths?: string[] | null; num_last_images_to_include?: number | null; transparent_background?: boolean }) => { image_url: string; output_hint?: string }`. There is no size, aspect-ratio, quality, model, `n` or seed argument. Guidance in the declaration: use `referenced_image_paths` "when every target image has a local file path"; `num_last_images_to_include` is "up to 5"; "Never provide both"; "imagegen needs a few minutes to finish". — [local: session rollout JSONL, 25 Nov 2026](file://~/.codex/sessions/2026/11/25/rollout-2026-11-25T20-29-43-01a21338-4073-7cf1-8d0a-a2fefc1de9a0.jsonl)
- Third-party summary of the same mechanism: tool is `image_gen`, invoked with `codex '$imagegen ...'` or `codex exec '$imagegen ...'` or by natural language; "there is no codex image subcommand"; shipped as a built-in skill in v0.117.0 (26 Mar 2026) and moved to gpt-image-2 in v0.123.0 (23 Apr 2026); v0.136 added a feature-gated standalone image extension; v0.137 widened hosted image tools to more code-mode flows. — [Daniel Vaughan, Codex CLI visual workflows (4 Jun 2026, third-party)](https://codex.danielvaughan.com/2026/06/04/codex-cli-visual-workflows-image-input-gpt-image-2-generation-asset-pipelines-v0137/); [earlier article, 27 Apr 2026](https://codex.danielvaughan.com/2026/04/27/codex-cli-image-generation-gpt-image-2-visual-development-workflows/)

- `codex exec [OPTIONS] [PROMPT]` ("Run Codex non-interactively"; prompt can come from stdin with `-`); `-i, --image <FILE>...` "Optional image(s) to attach to the initial prompt"; `-m, --model`; `-s, --sandbox <read-only|workspace-write|danger-full-access>`; `-C, --cd <DIR>`; `--add-dir <DIR>`; `--skip-git-repo-check`; `--ephemeral` (no session files persisted); `--json` ("Print events to stdout as JSONL"); `-o, --output-last-message <FILE>`; `--output-schema <FILE>`; `--enable/--disable <FEATURE>`; `-c key=value`; subcommands `resume`, `fork`, `review`. — [local: `codex exec --help`](file://~/.local/bin/codex)

### Inferences
- A workable headless command shape, assembled from the help text and skill docs (NOT run end-to-end here): `codex exec --skip-git-repo-check --sandbox workspace-write -C <project> --json -o logs/<shot>.txt '<prompt beginning "Use $imagegen ..." and ending "copy the final image to frames/<shot>.png">' -i refs/charA.png,refs/kitchen.png | tee logs/<shot>.jsonl`. Because `-i` is declared as `<FILE>...` (variadic), put the prompt before `-i` or pipe the prompt on stdin so it is not swallowed as a file name.
- Since the built-in tool has no size argument, 9:16 must be requested in the prompt text ("vertical 9:16 frame"). Local evidence shows this can return exact 9:16 (`941x1672`) but also near-misses (`910x1728`, `965x1629`, `853x1844`), so every frame needs a post-step that verifies dimensions and center-crops/pads to 9:16.
- Built-in outputs are about 1.5–1.6 MP, i.e. below 1080x1920 (2.07 MP). Any Codex-route frame needs upscaling before it can fill a 1080x1920 canvas, let alone leave pan/zoom margin (see section 7).
- The model behind the built-in tool is server-side and not selectable. Given OpenAI's rollout statements it is probably Images 2.6 as of late November 2026, but nothing on this machine confirms it; the CLI's bundled skill text lags (still says gpt-image-2).
- Budget feel for the plan route: at 34–139 s per image and one image per tool call, 300 frames is roughly 3–12 hours of wall time if run serially, before retries and before hitting five-hour/weekly windows on Plus. Because each image costs "3-5x" a normal turn and the agent also spends tokens reading reference images, a Plus plan is unlikely to finish 250–400 frames plus retakes without hitting limits or buying credits; this is an estimate, not a measured figure.
- Rough credit cost per image if billed from credits: gpt-image-2 at 1024x1536 costs about $0.041 (medium) or $0.165 (high) at $30 per 1M output tokens, i.e. about 1,370 or 5,500 output tokens, which at 750 credits per 1M is about 1 or 4 credits per image, plus input-image tokens for references. A search snippet of the same rate card mentioned "Images | 1 generation | 5 credits", which is in the same range but was not visible on the fetched page.
- The file prefix differs by client (`exec-<uuid>.png` from the desktop app's code-mode cell; `ig_*.png` reported for the CLI). A batch script should not hard-code either; it should glob the session folder or parse `savedPath` from the JSONL.

### Gaps
- Not verified by a live run: whether `codex exec` on 0.160.1 writes the PNG to `~/.codex/generated_images/` (two third-party sources conflict), and what event names appear in `--json` output for image items. A single-image smoke test resolves this.
- No official page states a numeric image allowance per plan for Codex; only the "3-5x faster" multiplier and token credit rates exist. Business/Pro 5x/Pro 20x image-specific numbers were not found.
- The official Codex CLI docs page for image generation could not be located (the old `developers.openai.com/codex/...` URLs redirect or 404); findings rely on the bundled skill text and third-party articles.
- Could not open GitHub issue #37717 directly to confirm its current status or whether it is fixed in 0.160.x.

## 2. OpenAI's current best image model: IDs, sizes / 9:16, quality tiers, cost, reference-image capabilities

### Takeaway
As of November 2026 the current API models are `gpt-image-2.6-sunburst` (quality/editing consistency) and `gpt-image-2.6-flare` (speed), with `gpt-image-2.5-sunburst` / `gpt-image-2.5-flare` (snapshot `2026-09-08`) and `gpt-image-2` still listed; all share $30 per 1M image-output tokens. Native 9:16 is supported through custom `WIDTHxHEIGHT` sizes (multiples of 16, up to `2160x3840`), so `1024x1536` (2:3) is no longer the closest option; exact `1080x1920` is not valid because 1080 is not a multiple of 16.

### Cited Findings

**Models and positioning**
- Official pricing page lists `gpt-image-2.6-sunburst`, `gpt-image-2.6-flare`, `gpt-image-2.5-sunburst`, `gpt-image-2.5-flare`, `gpt-image-2`, `gpt-image-1.5`, `gpt-image-1-mini`. — [OpenAI API pricing](https://developers.openai.com/api/docs/pricing)
- GPT-Image-2.5 Sunburst: "Our most capable model for image generation and editing" (as written on its own page), alias `gpt-image-2.5-sunburst`, default snapshot `gpt-image-2.5-sunburst-2026-09-08`; quality settings `low`, `medium`, `high`, `xhigh`, `max`, `auto`; endpoints `v1/images/generations`, `v1/images/edits`, `v1/batch`. — [OpenAI model page: GPT-Image-2.5 Sunburst](https://developers.openai.com/api/docs/models/gpt-image-2.5-sunburst)
- GPT-Image-2.6 Sunburst: "Image generation and editing for detailed visual work"; supports generations and edits endpoints; listed features: complexity setting, markup-guided edits, SVG output, animated GIF output; the page marks Batch as not supported and gives no per-tier rate limits. — [OpenAI model page: GPT-Image-2.6 Sunburst](https://developers.openai.com/api/docs/models/gpt-image-2.6-sunburst)
- Images 2.5 (8 Sep 2026): "better preservation of subjects from reference photos", edits "change only what was requested", latency "up to 50% lower" than Images 2.0. Flare is "the default for most applications"; Sunburst is for "premium workflows that need tighter control across edits" with longer generation times. — [OpenAI, Images 2.5](https://openai.com/index/introducing-chatgpt-images-2-5/)
- Images 2.6 (4 Nov 2026): 50% faster; Flare can produce low-quality images "in as little as six seconds"; Sunburst gives "higher-quality generation and greater consistency across edits at medium or high quality"; adds GIF output, SVG export, markup editing in the API and a `complexity` parameter; aims to "keep characters, products, and brand details consistent" as users edit. — [OpenAI, Images 2.6](https://openai.com/index/introducing-images-2-6/)
- `gpt-image-1` was shut down on 23 Oct 2026 (per the guide); a third-party tracker lists `gpt-image-1.5`, `gpt-image-1-mini` and `chatgpt-image-latest` as retiring 1 Dec 2026. — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation); [developersdigest (third-party, retirement dates unverified)](https://www.developersdigest.tech/models/image-generation/openai)
- DALL·E 2 and 3 were retired from the API on 12 May 2026. — [Daniel Vaughan (third-party)](https://codex.danielvaughan.com/2026/06/04/codex-cli-visual-workflows-image-input-gpt-image-2-generation-asset-pipelines-v0137/)

**Sizes and aspect ratios**
- For Sunburst and Flare (2.5 and 2.6): recommended sizes `1024x1024`, `1536x1024`, `1024x1536`; custom `WIDTHxHEIGHT` strings are allowed (example `1536x864`); width and height must be multiples of 16; aspect ratio between 1:3 and 3:1; neither edge above 3840 px; total pixels between 655,360 and 8,294,400; "For GPT-Image-2.5, resolutions above `2560x1440` are experimental." — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)
- For `gpt-image-2`: popular sizes `1024x1024`, `1536x1024`, `1024x1536`, `2048x2048`, `2048x1152`, `3840x2160`, `2160x3840`, `auto` (default); same constraints (max edge 3840, multiples of 16, ratio at most 3:1, 655,360–8,294,400 pixels). — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation); [local: imagegen `references/image-api.md`](file://~/.codex/skills/.system/imagegen/references/image-api.md)
- The prompting guide lists `2160x3840` as 4K portrait for GPT-Image-2.5 and repeats that outputs above 2560x1440 are experimental. — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- Older models (`gpt-image-1.5`, `gpt-image-1-mini`) only support `1024x1024`, `1024x1536`, `1536x1024`, `auto`. — [local: imagegen `references/image-api.md`](file://~/.codex/skills/.system/imagegen/references/image-api.md)

**Quality, complexity, formats**
- Quality tiers: Sunburst/Flare `low`, `medium`, `high`, `xhigh`, `max`, `auto` (default `auto`); `gpt-image-2` `low`, `medium`, `high`, `auto`. — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)
- `complexity` accepts `low`, `medium`, `high`; "If you omit `complexity`, both models use `high`"; no separate fee; use `low` for targeted edits "so surrounding details stay intact"; "Use `xhigh` or `max` only when they fix an unmet requirement within your latency budget." — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation); [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- `output_format` `png` (default), `jpeg`, `webp`; `output_compression` 0–100 for JPEG/WebP; `background` `transparent|opaque|auto`; `n` for multiple images; streaming with `partial_images` 0–3 (each partial adds 100 image output tokens). — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)

**Pricing**
- Standard rates per 1M tokens for `gpt-image-2.6-*`, `gpt-image-2.5-*` and `gpt-image-2`: text input $5.00, image input $8.00, cached text $1.25, cached image $2.00, image output $30.00. `gpt-image-1.5`: image output $32.00. `gpt-image-1-mini`: text $2.00, image input $2.50, output $8.00. Batch rates are half (image output $15.00 for the 2.x models). — [OpenAI API pricing](https://developers.openai.com/api/docs/pricing)
- Per-image output prices are only published for older models (1024x1024 / 1024x1536 / 1536x1024): GPT-Image-2 low $0.006 / $0.005 / $0.005, medium $0.053 / $0.041 / $0.041, high $0.211 / $0.165 / $0.165; GPT Image 1.5 low $0.009 / $0.013 / $0.013, medium $0.034 / $0.05 / $0.05, high $0.133 / $0.2 / $0.2; GPT Image 1 mini low $0.005 / $0.006 / $0.006, medium $0.011 / $0.015 / $0.015, high $0.036 / $0.052 / $0.052. — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)
- For GPT-Image-2.5: "Token rates match GPT Image 2, but the GPT Image 2 calculator doesn't estimate GPT-Image-2.5 usage." No per-image table for 2.5/2.6 exists on the fetched pages. — [OpenAI model page: GPT-Image-2.5 Sunburst](https://developers.openai.com/api/docs/models/gpt-image-2.5-sunburst)

**Reference images, edits, fidelity**
- Edits endpoint `POST /v1/images/edits` (`client.images.edit`); "For GPT Image models, you can provide up to 16 images"; one optional `mask` (applies to the first image, must have an alpha channel, same size/format, under 50 MB; "Masking is prompt-guided; exact shapes are not guaranteed"). — [local: imagegen `references/image-api.md`](file://~/.codex/skills/.system/imagegen/references/image-api.md); [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)
- `input_fidelity`: "For `gpt-image-2`, omit this parameter ... every image input is processed at high fidelity automatically", so "image input tokens can be higher for edits that include reference images"; the prompting guide says to omit `input_fidelity` on image edits for the newer models too. For `gpt-image-1.5` the option is `low|high` and it "preserves the first 5 input images with higher fidelity". — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation); [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md); [local: imagegen `references/image-api.md`](file://~/.codex/skills/.system/imagegen/references/image-api.md)
- Markup-guided edits (2.5 and 2.6): send a transparent annotation layer as `markup`, same pixel size as the first input image (each at most 16,777,216 pixels, annotation file at most 50 MB); "Do not combine `markup` with `mask`"; additional images serve as references. — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)
- A third-party test of GPT Image 2.5 on a reseller platform reports "up to 16 references (JPG, PNG, or WebP, 10 MB each)". — [JXP storyboard test, 15 Sep 2026 (vendor blog)](https://www.jxp.com/gpt-image/blog/gpt-image-2-5-storyboard)
- Responses API: the `image_generation` tool takes a `model` field and an `action` of `auto|generate|edit`; multi-turn editing works via `previous_response_id` or by passing prior image-generation call items; the mainline model may rewrite prompts (exposed as `revised_prompt`). — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)

**Rate limits (API)**
- GPT-Image-2.5 Sunburst default limits by tier: Build 250,000 TPM / 20 images per minute; Launch 3,000,000 TPM / 150 IPM; Grow 8,000,000 TPM / 250 IPM. — [OpenAI model page: GPT-Image-2.5 Sunburst](https://developers.openai.com/api/docs/models/gpt-image-2.5-sunburst)
- A third-party article (gpt-image-2 era) cites "250 images/min for established accounts, 5/min for new accounts". — [Daniel Vaughan (third-party, June 2026)](https://codex.danielvaughan.com/2026/06/04/codex-cli-visual-workflows-image-input-gpt-image-2-generation-asset-pipelines-v0137/)
- "Using GPT Image models may require API Organization Verification." — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)

### Inferences
- Valid exact-9:16 sizes under the multiples-of-16 rule are `720x1280`, `864x1536`, `1008x1792`, `1152x2048`, `1296x2304`, `1440x2560` and `2160x3840` (width = 144·m, height = 256·m). `1080x1920` is rejected (1080 / 16 = 67.5); `1088x1920` is valid but slightly wider than 9:16. `1440x2560` is the largest 9:16 size that is not above the "experimental" 2560x1440 threshold for GPT-Image-2.5.
- Cost for the whole job on the API is small. Using the published gpt-image-2 portrait prices as a proxy (same token rates): 400 frames at medium (about $0.041) is about $16; at high (about $0.165) about $66. Larger sizes cost more because output tokens scale with pixels: `1440x2560` has about 2.3x the pixels of `1024x1536`, so roughly $0.10 (medium) to $0.39 (high) per frame if scaling is linear, i.e. about $40–$155 for 400 frames. Reference-image input tokens ($8 per 1M, always high fidelity) and retakes (plan for 1.5–2x) add to this. These are estimates; OpenAI publishes no per-image table for 2.5/2.6.
- For this project Sunburst (2.6 or 2.5) is the better fit for identity-sensitive shots because OpenAI positions it for consistency across edits; Flare at `low` is appropriate for cheap layout drafts.
- There is a documentation inconsistency: the Sunburst model pages mark the Responses endpoint as "not supported" while the guide says the model can be selected inside the Responses `image_generation` tool. The Images API (`/v1/images/edits`) is the unambiguous route.

### Gaps
- No official per-image price or output-token table for GPT-Image-2.5/2.6 at 9:16 sizes was found; use the calculator in the guide or measure `usage` on a few real calls.
- IPM limits for Flare and for the 2.6 models, and whether 2.6 lifts the "experimental above 2560x1440" caveat, were not found.
- Maximum reference-image count is stated as 16 for "GPT Image models" in the bundled reference and a vendor test; the fetched portion of the official guide for 2.5/2.6 did not restate the number.
- Whether Batch API works for 2.6 (model page says no; pricing page lists batch rates for 2.6) is unresolved.

## 3. Documented techniques for character and location consistency across many generations

### Takeaway
There is no seed parameter and no trained-character feature; consistency comes from passing approved reference images on every call (edits endpoint, up to 16 images, each labelled by index and role), repeating a short fixed identity/wardrobe/style block, and using targeted edits rather than regeneration for fixes. OpenAI itself warns the model "may occasionally struggle to maintain visual consistency for recurring characters", and independent tests show props and set dressing drift more than faces, so location and prop references plus human review are needed.

### Cited Findings

**OpenAI's own guidance**
- For multi-image projects: create a reusable character reference "to help preserve appearance across scenes, poses, and pages", reuse the generated character image as an input for new scenes, restate defining details (examples: "Same green hooded tunic", "Same facial features, proportions, and color palette") and add "Do not redesign the character." — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- Multi-image inputs: "Identify each input by number and purpose" (subject, style, clothing, background) and say how they combine (example: place the dog from image 2 into the scene from image 1). — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- Identity preservation wording used in OpenAI's example: "Do not change her face, facial features, skin tone, body shape, pose, or identity in any way"; "State which facial features and proportions must remain unchanged." — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- Multi-turn: use the previous output as the next input, request one change per turn, restate details to preserve; "Repeated edits can drift"; "If a region must stay pixel-identical, composite the approved edit into the original instead of relying on prompting." — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- Style: describe it in a labelled "Style:" section and restate style constraints on later turns if the result drifts; for style transfer give the reference image one role (palette, texture or medium). — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- Stated limitation: "the model may occasionally struggle to maintain visual consistency for recurring characters or brand elements across multiple generations"; it "may have difficulty placing elements precisely in structured or layout-sensitive compositions". — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)
- Codex skill guidance mirrors this: label every input image's role (reference image / edit target / supporting insert), "For multi-image inputs, reference images by index and describe how they should be used", "For edits, repeat invariants every iteration to reduce drift", "Iterate with single-change follow-ups"; edit taxonomy includes `identity-preserve` ("lock face/body/pose") and `style-transfer`. — [local: imagegen SKILL.md](file://~/.codex/skills/.system/imagegen/SKILL.md)

**Seeds / reproducibility**
- Neither the image generation guide nor the prompting guide mentions a seed parameter; the code samples do not set one, and `n` is the only variation control. — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md); [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)
- The bundled parameter list for GPT Image models (`prompt`, `model`, `n` 1–10, `size`, `quality`, `background`, `output_format`, `output_compression`, `moderation`, plus edit-only `image`, `mask`, `input_fidelity`) contains no seed. — [local: imagegen `references/image-api.md`](file://~/.codex/skills/.system/imagegen/references/image-api.md)
- Codex image generation is "not suited to ... tasks needing pixel-perfect reproducibility". — [Daniel Vaughan (third-party)](https://codex.danielvaughan.com/2026/06/04/codex-cli-visual-workflows-image-input-gpt-image-2-generation-asset-pipelines-v0137/)

**Practitioner tests and guides (2026)**
- JXP test of GPT Image 2.5 Flare (15 Sep 2026, single run per setup, vendor blog): workflow is (1) a three-view character sheet (front, three-quarter, profile) on a plain background, about 25 s; (2) a constant "continuity lock" block fixing identity, wardrobe, location, palette and lighting; (3) one action and one framing per panel; (4) a multi-panel sheet first for planning, then regenerate keepers at full resolution. — [JXP storyboard test](https://www.jxp.com/gpt-image/blog/gpt-image-2-5-storyboard)
- Same test, measured: a 6-panel sheet took 32.5 s and a 9-panel sheet 31.5 s (one credit each) versus 3 min 13 s for 6 separate frames; the separate frames were sharper but drifted more — a white ceramic cup became a paper cup, the espresso machine and counter colour changed, a close-up inherited the grey backdrop of the reference sheet, and camera-position phrases ("from behind the counter", "high angle") were not reliably followed. — [JXP storyboard test](https://www.jxp.com/gpt-image/blog/gpt-image-2-5-storyboard)
- Same test: errors in the reference sheet are copied into every panel (wrong shoes repeated everywhere), and a blanket constraint ("Do not add extra characters") emptied a scene that was supposed to be busy; recommendations are to describe every prop in every separate frame, load a location reference, "describe what is visible in the frame, not where the camera sits", and scope constraints per panel. Opening line used: "Use the uploaded character image as the permanent identity reference." — [JXP storyboard test](https://www.jxp.com/gpt-image/blog/gpt-image-2-5-storyboard)
- IMG.LY benchmark (26 models, one precisely described character rendered in 3 scenes, 9 runs per model, text-only description, 5-point scale): character consistency is the lowest-scoring capability; common failures are "changed outfits, shifting faces, and missing props"; drift builds gradually across scenes; advice is to generate the character once, cut it out and reuse it as an asset, and to fix details by hand instead of regenerating. (IMG.LY sells the editing tools it recommends.) — [IMG.LY consistency findings](https://img.ly/ai-benchmarks/findings/consistency.md)
- General guides agree that an approved reference image attached to every frame is the most reliable anchor, and that overly long re-descriptions can fight the reference ("Keep character descriptions brief in prompts. Let the reference image do the heavy lifting") — the latter written for Nano Banana, not OpenAI. (Search-result summaries; pages not opened.) — [fal.ai character consistency guide](https://fal.ai/learn/tools/ai-character-consistency); [Flowith Nano Banana storyboard guide](https://flowith.io/blog/nano-banana-consistent-characters-storyboard)
- One guide's own estimate (not measured): GPT Image 2 "gets you 80–90% of the way" on storyboard consistency, with the image-to-video model's reference feature closing the rest. — [NemoVideo (third-party, search summary)](https://www.nemovideo.com/blog/gpt-image-2-storyboard)

**Codex-route specifics**
- The built-in tool accepts local reference files through `referenced_image_paths` (array of paths) or the last up-to-5 conversation images through `num_last_images_to_include`; a real call on this Mac passed a previously generated frame as `referenced_image_paths` with the prompt "Use the supplied photo as casting, costume, lighting and cinematic grain reference". — [local: session rollout JSONL](file://~/.codex/sessions/2026/11/25/rollout-2026-11-25T20-29-43-01a21338-4073-7cf1-8d0a-a2fefc1de9a0.jsonl)

### Inferences
- A practical asset hierarchy for two series: per character one approved turnaround sheet plus one clean face close-up per costume; per location one or two approved "master plates" (wide establishing views, empty of characters); per series one style plate. Each shot call then passes [character sheet(s) in shot] + [location plate] + [style plate, illustration series only], well inside the 16-image limit.
- OpenAI advises repeating defining details while the Nano Banana guide warns against over-describing. A reasonable reconciliation for OpenAI models is a short fixed identity block (5–8 concrete attributes: hair, build, age band, costume pieces and colours, one or two distinguishing marks) pasted verbatim from a character bible, with everything else left to the reference image. This is a synthesis, not a tested result.
- Because sheets hold props better but lose resolution, a useful pattern is to generate a low-cost multi-panel sheet per scene as a continuity guide, approve it, and then pass that sheet as an additional reference when rendering each full-resolution frame.
- Chained editing (frame N as input to frame N+1) accumulates drift; always anchoring to the original approved references rather than to the previous frame should limit this. Use previous-frame input only for true continuity edits (same shot, changed expression or prop).
- Fixes should be edits with explicit invariants ("change only the dupatta colour; keep face, pose, background unchanged") with `complexity: low`, since OpenAI says low complexity keeps surrounding details intact.

### Gaps
- No controlled measurement was found of identity retention for GPT-Image-2.5/2.6 over dozens of reference-conditioned frames; the IMG.LY benchmark is text-only (no reference images) and the JXP test is a single run.
- No evidence was found on how many distinct characters can be held in one frame from separate reference sheets with OpenAI models (Google documents "up to 5 people"; OpenAI gives no figure).
- No source tests consistency for South Asian faces specifically.

## 4. Prompting for cinematic photorealism (South Asian cast, Indian locations) and for a stable flat 2D cel-shaded style

### Takeaway
OpenAI's guidance for realism is to ask explicitly for a "real photograph", use camera/lens/lighting words as appearance cues, describe skin texture and worn materials, and exclude glamorisation and retouching; for illustration it is to name medium, line quality, palette and proportions in a fixed "Style:" block and restate it when drift appears. No authoritative source covers South Asian subjects or Indian settings specifically, so those practices are inference plus one working local example.

### Cited Findings
- Photorealism: request "photorealistic" or "real photograph" explicitly; use cues such as "35mm film photograph, medium close-up at eye level, using a 50mm lens", soft daylight, shallow depth of field, subtle film grain; camera specifications are "cues for appearance, not a guarantee of exact physical simulation". — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- To avoid an idealised look, exclude glamorisation and heavy retouching and describe visible skin texture and worn materials; for wide, low-light, rainy or neon scenes specify scale, atmosphere and colour instead of mood words. — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- One OpenAI example for candid realism says the image "should look like a real photograph someone could have taken" and to "Avoid cinematic lighting, dramatic color grading, or stylized composition" — i.e. cinematic grading is a deliberate stylistic choice that trades away candid realism. — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- People framing: describe body framing, relative scale, gaze and interaction with objects (example "full body visible, feet included"); the guide has no separate skin-tone guidance beyond preserving the subject's existing skin tone in edits. — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- Historical or culturally specific settings "may contain inaccuracies, so check clothing and staging"; small text and signage need checking for spelling and legibility. — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- Illustration: specify the medium, line quality and proportions (example "hand-painted watercolor look, soft outlines, warm earthy colors"); for flat graphics ask for flat design, clean vector-like shapes, strong silhouette, minimal strokes, and avoid gradients unless essential. — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- Codex skill prompt schema (shared by both modes): labelled lines `Use case`, `Asset type`, `Primary request`, `Input images`, `Scene/backdrop`, `Subject`, `Style/medium`, `Composition/framing`, `Lighting/mood`, `Color palette`, `Materials/textures`, `Text (verbatim)`, `Constraints`, `Avoid`; ordering advice "scene/backdrop -> subject -> details -> constraints"; "Use camera/composition language for photorealism"; taxonomy slugs include `photorealistic-natural` and `illustration-story` ("comics, children's book art, narrative scenes"). — [local: imagegen SKILL.md](file://~/.codex/skills/.system/imagegen/SKILL.md)
- A prompt that worked on this Mac on 25 Nov 2026 for an Indian photoreal still (status completed, no refusal): "An Indian woman in her early thirties, dark shoulder-length wavy hair, wearing a dark textured teal blouse, framed from the waist up ... Layered 1970s Bombay apartment updated in the present, half-lit, authentic, quietly atmospheric, textured 35mm film grain, medium contrast like a carefully lit cinema still, warm ochres and midnight greens ... Clear luminous realistic face, individual expression. No captions, titles, logos, writing, graphics or border." — [local: session rollout JSONL](file://~/.codex/sessions/2026/11/25/rollout-2026-11-25T20-29-43-01a21338-4073-7cf1-8d0a-a2fefc1de9a0.jsonl)
- Camera-position instructions are unreliable ("from behind the counter", "high angle" not followed); describing what is visible in frame works better. — [JXP storyboard test](https://www.jxp.com/gpt-image/blog/gpt-image-2-5-storyboard)
- In OpenAI's own comparison Flare and Sunburst outputs "can differ across models", so one model should be used for a whole series. — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)

### Inferences
- Photoreal series: keep one fixed "look block" for the series (film stock/grain, contrast, palette, lens family, aspect) and vary only scene, action and framing. Specify region- and class-specific detail rather than the word "Indian" alone (city or state, building type and era, fabric and garment names, jewellery, signage script, time of day, monsoon haze or tube-light colour), since generic prompts tend toward generic or touristic imagery. State skin tone, age and build concretely in the character bible and name visible skin texture to avoid the retouched look. This is practice-based inference; no source measured it.
- Ask for no legible signage or text unless needed, because Devanagari and other Indic text rendering was not covered by any source and OpenAI flags small text as error-prone.
- Flat 2D series: write a style block that names the things that drift — outline weight and colour ("uniform bold black outlines"), shading model ("two-tone cel shading, hard-edged shadows, no gradients, no airbrushing"), palette (list 6–10 named colours), eye and face construction, background treatment — and attach a style plate image on every call with the role "style reference only". Explicitly exclude "3D render, photorealism, painterly texture, soft shading", since the common drift for these models is toward semi-realistic rendering.
- Avoid naming a living artist or a specific studio/franchise look in the style block (policy and IP risk, see section 5); describe the visual attributes instead.
- Pin the model ID (use a dated snapshot such as `gpt-image-2.5-sunburst-2026-09-08` where one exists), quality and size for the entire series; a mid-series model change (for example the Codex built-in tool silently moving from 2.5 to 2.6) is a plausible source of style shift that the API route can avoid and the Codex route cannot.

### Gaps
- No reliable source was found on GPT-Image-2.5/2.6 behaviour with South Asian faces, skin tones, Indian clothing or Indian locations (bias, accuracy, typical errors). The single local example shows it can work but is not a test.
- No source evaluates stability of a flat cel-shaded style over dozens of OpenAI generations.
- Quality of Devanagari/Hindi text rendering in the 2.5/2.6 models was not researched.

## 5. Content-policy limits that matter for a drama, and how refusals show up

### Takeaway
On the API a block is a hard, non-retryable error — `error.code = "moderation_blocked"` (HTTP 400, usually `error.type = "image_generation_user_error"`) with an optional `moderation_details` object giving the stage (`input` or `output`) and coarse categories such as `violence` or `sexual`; the only knob is `moderation: "auto" | "low"`. Written policy bans sexualising or endangering anyone under 18, non-consensual photoreal likeness of real people, impersonation and political campaigning; nothing found specifically prohibits fictional police uniforms, flags or prop weapons, but developers report false positives on innocuous prompts, so the batch script must treat blocks as "rewrite the prompt", not "retry".

### Cited Findings
- "All prompts and generated images are filtered under the content policy." The `moderation` parameter accepts `auto` (default; "standard filtering that seeks to limit certain categories of potentially age-inappropriate content") and `low` ("less restrictive filtering"). — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)
- Blocked requests return `error.code = "moderation_blocked"`, usually with `error.type = "image_generation_user_error"`; optional `moderation_details` includes `moderation_stage` (`input`, `output`, or `unknown`) and coarse `categories` such as `harassment`, `self-harm`, `sexual`, `violence`. "User errors should not be retried automatically without changing the prompt or inputs. Rate-limit and server failures should be retried with backoff. Quota errors should not be retried automatically." — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)
- OpenAI Usage Policies (effective 20 Nov 2026; changelog shows an update on 21 Oct 2026): restricts "use of someone's likeness, including their photorealistic image" without consent; prohibits "sexualizing children", CSAM "whether or not any portion is AI generated", "underaged sexual or violent roleplay" and "exposing minors to age-inappropriate content", with protections for "anyone under 18"; prohibits "terrorism or violence, including hate-based violence", "weapons development, procurement, or use", "threats, intimidation, harassment, or defamation", "political campaigning, lobbying, foreign or domestic election interference", and "deceit, fraud, scams, spam, or impersonation"; prohibits infringing others' intellectual property. The page is a general policy and has no image-specific section or separate gore rule. — [OpenAI Usage Policies](https://openai.com/policies/usage-policies/)
- Developer reports: a benign aerobics prompt was blocked under the `sexual` category on gpt-image-2 even with `moderation: low`, while the same prompt succeeded in ChatGPT. — [OpenAI community thread: moderation over-refusals on gpt-image-2](https://community.openai.com/t/api-issue-moderation-over-refusals-on-gpt-image-2-with-moderation-low-where-chatgpt-always-succeeds/1388964)
- Prompts naming well-known pop-culture characters or scenes were blocked on gpt-image-1 even where DALL·E 3 allowed them. — [OpenAI community thread](https://community.openai.com/t/gpt-image-1-moderation-blocks-prompts-allowed-by-dall-e-3-pop-culture-references/1252701)
- Reseller documentation (not OpenAI) says the edits endpoint is among the strictest paths — "the same prompt + image might pass the generation endpoint but get blocked by moderation_blocked on the edits endpoint" — that `moderation: low` has limited effect on output-stage blocks, and that retrying an unchanged prompt will not help. — [APIYI GPT image moderation FAQ (third-party)](https://docs.apiyi.com/en/faq/gpt-image-content-moderation); [APIYI troubleshooting (third-party)](https://help.apiyi.com/en/fix-gpt-image-2-moderation-blocked-400-error-en.html)
- Real people: since March 2025 OpenAI has allowed images of adult public figures with an opt-out form, with "additional guardrails" for political public figures (2025 reporting; may have changed). — [TechCrunch, 28 Mar 2025](https://www.techcrunch.com/2025/03/28/openai-peels-back-chatgpts-safeguards-around-image-creation); [The Decoder](https://the-decoder.com/openai-outlines-new-image-generation-rules-for-chatgpt/)
- Provenance: outputs carry C2PA metadata and an invisible watermark. — [OpenAI, Images 2.5](https://openai.com/index/introducing-chatgpt-images-2-5/)
- In Codex the built-in tool's result item has a `failure` field (null on success) alongside `status`; six of six local generations of an Indian domestic-mystery scene completed with `failure: null`, and the prompt author had added "No violence." — [local: session rollout JSONL](file://~/.codex/sessions/2026/11/25/rollout-2026-11-25T20-29-43-01a21338-4073-7cf1-8d0a-a2fefc1de9a0.jsonl)

### Inferences
- For this project (fictional people, drama): depict aftermath and tension rather than graphic injury; keep weapons as incidental props in adult hands rather than the focus of a threatening close-up; keep any character under 18 out of violent, romantic or distressing frames entirely (the `auto` filter is explicitly tuned around "age-inappropriate content", so child + conflict is the likeliest false-positive zone); state adult ages explicitly ("in her early thirties") in every prompt and character sheet.
- Do not name real people, real politicians, real police forces' exact insignia, or copyrighted characters/studios. Describe a generic fictional uniform ("khaki uniform, generic shoulder patches, no readable insignia") — this is a caution derived from the likeness/impersonation/IP rules and from the pop-culture false positives, not from a documented rule about uniforms or flags.
- Edits with photoreal human reference images pass through stricter checks than text-only generation (per the reseller report), which matters because the consistency workflow relies on reference images of (synthetic) people on every call. Expect a higher block rate on the photoreal series than on the illustration series, and log `moderation_details` to see which stage fired.
- Use `moderation: "low"` on the API for a drama; the Codex built-in tool exposes no moderation setting.
- Script behaviour: on `moderation_blocked`, mark the shot `blocked`, store the stage/categories, and route it to a prompt-rewrite queue; never auto-retry the same payload (repeated violations could also put the account at risk — the usage policies allow enforcement, though no threshold is published).

### Gaps
- No OpenAI page was found that addresses national flags, police or military uniforms, or realistic firearms in fiction for image generation; the old image-policy URL (`openai.com/policies/creating-images-and-videos-in-line-with-our-policies`) now redirects to a notice about the Sora discontinuation.
- The image-specific system cards for Images 2.5/2.6 (at deploymentsafety.openai.com) were not read; they may contain the precise rules on minors and photoreal people.
- How a block appears inside `codex exec` output (message text, non-zero exit or not) was not observed.
- Whether the 2025 public-figure policy is unchanged in late 2026 was not verified (not relevant if all characters are fictional).

## 6. Batching, resumability, parallelism, cost tracking — Codex CLI versus direct API

### Takeaway
The direct Image API is the more controllable and more reliable route for 250–400 frames: explicit size/quality/model/moderation, structured errors, documented per-minute limits, per-call token usage for cost tracking and optional half-price Batch; it needs an API key on a billed (and possibly verified) organisation. The Codex route needs nothing new from the user but offers no size or quality control, shares an opaque plan quota, takes 0.5–2+ minutes per image through an agent loop, and has an open bug where a multi-image `codex exec` run exits 0 with files missing, so it must be wrapped in a filesystem-verifying, one-shot-per-frame manifest loop.

### Cited Findings

**Codex route**
- Open issue #37717 (CLI 0.147.0): six images requested in one non-interactive run, two produced, none at the requested paths, exit code 0. Recommended handling: check each expected file exists and is non-empty (`[[ -s "$path" ]]`), check the event stream (`jq -e 'select(.type == "turn.failed" or .type == "error")' codex-events.jsonl`), validate MIME type with `file --brief --mime-type`, record `shasum -a 256`, keep partial output, and send a bounded repair request naming only the missing paths. "The filesystem is authoritative for a filesystem deliverable." JSONL event names cited: `turn.completed`, `turn.failed`, `error`. — [Aident write-up of openai/codex #37717 (third-party)](https://aident.ai/blog/fix-codex-exec-exits-zero-missing-image-artifact)

### Inferences
- What the user must provide. Codex route: nothing new (ChatGPT login already present); optionally purchased credits or a higher plan if limits are hit. API route: an `OPENAI_API_KEY` from a platform account with billing/prepaid credit, organisation verification if prompted, and (to avoid the 20 IPM Build cap mattering) nothing more — 20 IPM already allows 400 frames in about 20 minutes of pure generation.
- Recommended architecture regardless of route — a manifest-driven, idempotent runner:
  - `shots.jsonl`: one row per frame with `shot_id` (e.g. `S1E03_SC02_SH014`), series, prompt body, list of reference asset IDs, size, quality, status (`pending|done|blocked|failed`), attempts, output path, sha256, usage/cost, error code.
  - Deterministic naming `frames/<series>/<episode>/<shot_id>_v<attempt>.png`; never overwrite; a "selected" pointer per shot.
  - Skip rows whose output exists and validates (dimensions, MIME, non-zero size) so the run is resumable after any crash or quota stop.
  - Prompt = fixed series style block + fixed character/location blocks pulled from a bible file + per-shot action/framing; store the fully rendered prompt and the model's `revised_prompt` with the result.
  - Retry policy: exponential backoff on 429/5xx (max 3–5), no retry on `moderation_blocked` or quota errors.
  - Cost tracking: on the API record the `usage` token counts per response and multiply by the rate card ($30 per 1M image output, $8 per 1M image input, $5 per 1M text input); on Codex only wall time and `/status` deltas are available.
- Parallelism: API — 3–5 concurrent requests is comfortably within the Build tier's 20 IPM and keeps the run under an hour; Codex — keep it serial (one frame per `codex exec` process, fresh session each time so reference images and base64 results do not accumulate in context), because the documented failure involved several images in one run and limits are shared with all other Codex work on the account.
- Writing a custom API runner is justified here even though the bundled skill says not to create one-off runners (that rule constrains the Codex agent, not the team): the bundled `generate-batch` has no reference-image support, defaults to `gpt-image-2`, and its handling of 2.5/2.6 model IDs, `xhigh`/`max` quality and `complexity` is unknown.
- Hybrid plan that costs nothing up front: build character sheets, location plates and style plates interactively in the Codex app/CLI (few images, high scrutiny), then render the 250–400 shot frames through the API with those sheets as references. Mixing routes risks a model mismatch (built-in tool on 2.6, API pinned to 2.5 or 2.6), so pin the API model to the same generation the sheets were made with and check a few frames for style match.

## 7. Upscaling and out-painting for slow pan/zoom at 1080x1920

### Takeaway
On the API the simplest answer is to generate larger than the output frame: `1440x2560` (exact 9:16, 1.33x linear margin, the largest size not flagged experimental for 2.5) or `2160x3840` (2x margin, experimental on 2.5), so no upscaler is needed for gentle moves. Codex built-in outputs are only about 1.5–1.6 MP (for example `941x1672`), below 1080x1920, so that route needs a 2x upscale (Real-ESRGAN locally for free, or Topaz) or a regeneration at higher resolution.

### Cited Findings
- Custom sizes up to 3840 px per edge and 8,294,400 total pixels are allowed (multiples of 16, ratio at most 3:1); `2160x3840` is the documented 4K portrait size; for GPT-Image-2.5 "resolutions above `2560x1440` are experimental". — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation); [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- "Large sizes and high quality increase latency and cost"; "Square images are typically fastest to generate." — [local: imagegen `references/image-api.md`](file://~/.codex/skills/.system/imagegen/references/image-api.md)
- The Codex built-in tool on this Mac returned vertical images of `941x1672`, `910x1728`, `965x1629`, `853x1844` and `1024x1536` — all about 1.5–1.6 MP. — [local: `~/.codex/generated_images`](file://~/.codex/generated_images)
- The built-in tool's own description lists "improving quality/resolution" among supported edits, but exposes no size argument. — [local: session rollout JSONL](file://~/.codex/sessions/2026/11/25/rollout-2026-11-25T20-29-43-01a21338-4073-7cf1-8d0a-a2fefc1de9a0.jsonl)
- Out-painting/extension is done through the edits endpoint with a mask whose transparent area marks what to fill; masks are prompt-guided, not pixel-exact, and apply to the first image. — [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation)
- "If a region must stay pixel-identical, composite the approved edit into the original instead of relying on prompting." — [OpenAI image prompting guide](https://developers.openai.com/api/docs/guides/image-prompting.md)
- Upscalers: Real-ESRGAN is free, open source and "fast enough for batch jobs of hundreds of images" locally; Topaz gives smoother, more polished results with face recovery at about $199/year; Real-ESRGAN keeps more texture but can exaggerate small artefacts, and upscaling noisy images "just gives you high-definition noise". (Search-result summaries of vendor/affiliate blogs; pages not opened.) — [botmonster: Real-ESRGAN vs Topaz vs SUPIR](https://botmonster.com/ai/local-ai-image-upscaling-real-esrgan-topaz-supir/); [WaveSpeed: Real-ESRGAN vs Topaz (vendor blog)](https://wavespeed.ai/blog/posts/real-esrgan-vs-topaz)
- A vendor test found that using a full-resolution still (rather than a small storyboard panel) as the image-to-video input carried composition and character design into the clip. — [JXP storyboard test](https://www.jxp.com/gpt-image/blog/gpt-image-2-5-storyboard)

### Inferences
- Margin arithmetic for a 1080x1920 output window: `1152x2048` gives 1.07x (about 7% push-in or a 72 px horizontal drift); `1296x2304` gives 1.2x; `1440x2560` gives 1.33x (enough for a slow 100% -> 120–130% push or a pan of up to 360 px horizontally / 640 px vertically at 1:1); `2160x3840` gives 2x. Slow micro-drama moves are typically 5–15%, so `1296x2304` or `1440x2560` is sufficient.
- For lateral pans, an alternative is to generate a wider-than-9:16 frame at the same height (for example `1728x2560`, a 27:40 frame; both values are multiples of 16, 4.42 MP, within limits) and compose it as an over-wide plate, instead of out-painting afterwards. Asking the model for "extra headroom and side margin around the subject, subject occupying the central 70% of frame" keeps faces out of the crop zone.
- Prefer generating large over out-painting later: mask edits are prompt-guided and can alter the original region, so out-painted frames need the approved centre composited back over the result. Out-painting is best reserved for rescuing an already approved frame that is framed too tightly.
- Codex-route frames: upscale 2x (for example `941x1672` -> `1882x3344`) with Real-ESRGAN on the Mac, then crop to exact 9:16. A general photo model suits the photoreal series; an anime/line-art model suits the cel-shaded series, where flat colour and hard outlines upscale cleanly. The choice of specific model weights is from general knowledge, not from a fetched source.
- Upscaling adds resolution but not true detail, and face-restoration features can alter identity; for photoreal faces native generation at `1440x2560` is the safer way to protect character likeness.

### Gaps
- No source measured GPT-Image-2.5/2.6 detail quality at `1440x2560` or `2160x3840` versus an upscaled `1024x1536`; the "experimental" label on large sizes suggests testing a few frames first.
- No source was found specific to preparing AI stills for Ken Burns style moves in vertical video, or comparing upscalers on OpenAI-generated images.
- Whether GPT-Image-2.6 can be asked through the Codex built-in tool for a higher-resolution output ("improving quality/resolution") and what size it returns was not tested.

## 8. Non-OpenAI alternatives for character-consistent story frames (comparison only)

### Takeaway
The one multi-model benchmark found puts Seedream 5.0 Pro first for text-described character consistency (4.86/5) with GPT Image 2.5 Sunburst in the leading group (4.72), ahead of GPT Image 2.5 Flare (4.17), Nano Banana Pro (3.89) and the FLUX.2 family (3.75); Google and Black Forest Labs, however, document stronger explicit multi-reference features (Nano Banana Pro: up to 14 input images and 5 consistent people; FLUX.2: up to 10 references). Evidence is thin and vendor-heavy, so OpenAI's current models look competitive rather than clearly behind, and no source justifies switching providers on consistency alone.

### Cited Findings
- IMG.LY consistency benchmark (26 models, same described character in 3 scenes, 9 runs each, 5-point adherence score, no date on page): Seedream 5.0 Pro 4.86; GPT Image 2.5 Sunburst, Qwen Image 3.0, Recraft V4.1 4.72; Grok Imagine Image 2.0 4.58; GPT Image 2 4.44; GPT Image 2.5 Flare, Muse Image 4.17; Nano Banana Pro, Nano Banana 2 Lite, Nano Banana 2.1 3.89; FLUX.2, FLUX.2 [pro], FLUX 3 Image, Seedream 4.5, Nano Banana 2, GPT Image 1.5, Ideogram 3.0 and others 3.75. "Every model drifts at some point." Midjourney and Flux Kontext are not included. — [IMG.LY consistency findings](https://img.ly/ai-benchmarks/findings/consistency.md)
- The same benchmark's headline (as indexed by search) calls Nano Banana Pro the best model at 3.89 across 15 models, which contradicts its own current table — the headline appears to predate newer models. — [IMG.LY consistency findings (web version)](https://img.ly/ai-benchmarks/findings/consistency/)
- Nano Banana Pro (Gemini 3 Pro Image, launched 20 Nov 2025): can blend up to 14 input images while keeping "the consistency and resemblance of up to 5 people"; output up to 4K; launch API pricing reported as $0.134 per 1K/2K image and $0.24 per 4K image (2025 figures; may have changed). — [Google developers blog: Build with Nano Banana Pro](https://blog.google/technology/developers/gemini-3-pro-image-developers/); [TechCrunch, 20 Nov 2025](https://techcrunch.com/2025/11/20/google-releases-nano-banana-pro-its-latest-image-generation-model/)
- FLUX.2 (Black Forest Labs, 25 Nov 2025): up to 10 reference images at once for character, product and style consistency (API docs: up to 8 references at 1 MP); vendor-published win rates put FLUX.2 [dev] at 59.8% versus FLUX.1 Kontext at 41.2% for single-reference editing, i.e. Kontext is the superseded generation. — [BFL: FLUX.2 announcement](https://bfl.ai/blog/flux-2); [BFL docs: character consistency](https://docs.bfl.ai/guides/usecases_editing_character_consistency); [BFL help: multi-reference editing](https://help.bfl.ai/articles/6546682167-what-is-multi-reference-editing)

(Search summaries; pages not opened.) — [Chase Jarvis: Nano Banana vs ChatGPT](https://chasejarvis.com/blog/nano-banana-vs-chatgpt-image-generation/); [OpenArt: GPT Image 2 vs Nano Banana 2](https://openart.ai/blog/gpt-image-2-vs-nano-banana-2/)
- Midjourney: one guide says it is "praised for style and character consistency when you use reference images and style-reference parameters"; no test data found. (Search summary; page not opened.) — [Dreamina guide (vendor)](https://dreamina.capcut.com/ai-image/ai-image-tools-character-consistency)
- Early-access partner comment on OpenAI's Images 2.6: Picsart reports "better character consistency". — [OpenAI, Images 2.6](https://openai.com/index/introducing-images-2-6/)

### Inferences
- The IMG.LY test uses text descriptions only, so it measures how well a model re-creates a described person without references. The project's workflow passes reference images on every call, which is where Nano Banana Pro's and FLUX.2's documented multi-reference features would matter; no comparable reference-conditioned benchmark including GPT-Image-2.5/2.6 was found, so the ranking for this exact workflow is unknown.
- Practical differences for this team: OpenAI is reachable today with no new account (Codex/ChatGPT login) and has native 9:16 up to 4K; Google documents an explicit multi-person limit (5) that OpenAI does not; FLUX.2 has open-weight variants for local or fine-tuned use. None of the alternatives offers a consistency guarantee that removes the need for reference sheets and human review.
- If OpenAI results drift unacceptably on a pilot scene (same 10 shots, same references), the most informative single comparison would be Nano Banana Pro or its successor and Seedream 5.0 Pro on the same shot list.
